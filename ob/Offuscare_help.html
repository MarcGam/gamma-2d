La premessa da fare è onesta: un file JavaScript eseguito nel browser non può essere offuscato al 100% in modo irreversibile. Per definizione, il browser deve poterlo decifrare ed eseguire, quindi un attaccante determinato potrà sempre, prima o poi, risalire alla logica. Quello che puoi fare è alzare così tanto il costo dell'attacco da rendere il reverse engineering non conveniente.

Il tuo gamma-2d_ob.js attuale è offuscato con tecniche di base (probabilmente javascript-obfuscator con opzioni non massimali). Ecco i livelli successivi, dal più semplice al più robusto.

🛠️ Livello 3 — javascript-obfuscator con preset "massima protezione"

È il tool open-source più diffuso (1M+ download/settimana). La differenza tra il tuo file attuale e una versione davvero robusta sta nella configurazione. Ecco un preset "max" da usare:

npx javascript-obfuscator gamma-2d.js --output gamma-2d_ob.js \
  --compact true \
  --control-flow-flattening true \
  --control-flow-flattening-threshold 1 \
  --dead-code-injection true \
  --dead-code-injection-threshold 0.4 \
  --debug-protection true \
  --debug-protection-interval 4000 \
  --self-defending true \
  --string-array true \
  --string-array-encoding rc4 \
  --string-array-rotate true \
  --string-array-shuffle true \
  --string-array-wrappers-type variable \
  --split-strings true \
  --split-strings-chunk-length 8 \
  --numbers-to-expressions true \
  --identifier-names-generator hexadecimal \
  --rename-globals false

Cosa attivano le opzioni chiave:

  • controlFlowFlatteningThreshold: 1: trasforma la struttura del codice in una macchina a stati con switch, rendendo il flusso logico quasi illeggibile.
  • debugProtection + selfDefending: se qualcuno apre i DevTools o prova a "beautificare" il codice, l'esecuzione si blocca o si rompe.
  • stringArrayEncoding: 'rc4': le stringhe non sono in chiaro ma cifrate con RC4 e decifrate a runtime.
  • deadCodeInjection: inserisce rami di codice mai eseguiti che confondono l'analisi statica.

⚠️ Attenzione alle performance: controlFlowFlattening può rallentare l'esecuzione fino a 1.5x. Per una libreria come gamma-2d (che gira a 60 FPS) testa bene prima di distribuire.

🧠 Livello 4 — VM-based Obfuscation (il salto di qualità)

Qui il codice JavaScript non viene più offuscato: viene compilato in bytecode che gira dentro una macchina virtuale custom embedded nel file. Il risultato non è più "JavaScript offuscato", ma un programma per una VM che solo quella VM sa eseguire.

Tool open-source/accessibili:

  • vm-obfuscator-pro (npm): compila JS in bytecode cifrato con opcode dinamici, decoy, anti-debug a 7 vettori, e ha un preset max che attiva tutto. Comando:

    npx vmobf gamma-2d.js -o gamma-2d_ob.js --preset max

  • Obfuscator.io Pro (a pagamento, API): la versione Pro di javascript-obfuscator aggiunge proprio la VM obfuscation con bytecode encryption e difese anti-LLM.

Questo è il livello massimo raggiungibile rimanendo su JavaScript puro. Il codice prodotto è molto più grande (spesso 3-5x) e più lento, ma il reverse engineering richiede competenze e tempo significativi.

🧱 Livello 5 — WebAssembly (il vero "scatola nera")

Se vuoi la massima protezione possibile senza soluzioni commerciali, la strada è compilare la logica critica in WebAssembly. Il binario Wasm non contiene nomi di variabili, commenti o struttura leggibile: è codice macchina per una VM stack-based.

Come si fa in pratica:

  1. Riscrivi la parte sensibile della libreria in AssemblyScript (un TypeScript-like che compila in Wasm) o in C/Rust.
  2. Compila in .wasm.
  3. Incorpora il .wasm come base64 nell'HTML e caricalo con WebAssembly.instantiate().
  4. La logica offuscata non è più JavaScript, ma un binario.

Limite importante: WebAssembly non può accedere direttamente al DOM, al canvas, o a console.log. Dovresti esporre queste API tramite "import" dal JavaScript host, il che complica molto l'architettura per una libreria grafica come gamma-2d. La ricerca accademica conferma che la transpilazione JS→Wasm è promettente per l'offuscamento ma ancora limitata (circa 1/3 del codice reale è convertibile automaticamente).

Per una libreria canvas come la tua, non è una strada pratica a meno di riscrivere grosse porzioni in AssemblyScript.

💼 Livello 6 — Soluzioni commerciali

Se il progetto ha valore commerciale, gli strumenti professionali offrono un pacchetto completo:

Tool Cosa offre di unico
Jscrambler Protezione client-side completa, anti-tamper, licensing, resistenza a LLM
PreEmptive JSDefender Offuscamento a strati + runtime integrity checks, usato in ambito enterprise
AxProtector JavaScript (Wibu) Crittografia del codice prima dell'esecuzione, con licensing integrato via CodeMeter

Questi tool partono da qualche centinaio di euro/anno e sono pensati per aziende che distribuiscono software commerciale.

💎 Riepilogo pratico per il tuo caso

Per gamma-2d, il miglior compromesso tra sforzo e risultato è:

  1. Sostituisci il comando di offuscamento attuale con la configurazione "max" di javascript-obfuscator (Livello 3). È un cambio di una riga nel tuo flusso di build e alza drasticamente l'asticella.
  2. Se vuoi esagerare senza riscrivere nulla, prova vm-obfuscator-pro con preset max (Livello 4) e confronta dimensione e performance. Se il gioco regge i 60 FPS, hai un livello di protezione vicino a quello commerciale.
  3. Non inseguire il "100%": nessun tool te lo può garantire. L'obiettivo realistico è rendere il codice "non vale la pena" da reversare rispetto al valore che contiene.

Il bundler che hai già funziona perfettamente con uno qualsiasi di questi output: ti basta sostituire il file gamma-2d_ob.js con la versione generata dal tool più aggressivo, senza toccare il codice Python. 🎯
